### Added (Sprint 3, Sahil, stream T)
- C02 Cryptographic Failures challenge (story 5.2 / T-20, FR-CHL-03, CWE-328): a gift-card wallet (migration 0004 adds `gift_cards` + a non-spendable `promo_credit` ledger) with `POST /api/wallet/buy` and `POST /api/wallet/redeem`. One isolated module (`challenges/c02-gift-card-codes.mjs`): the fixed build (default) issues random CSPRNG codes and stores only a keyed HMAC; the vulnerable build (`VM_CHALLENGE_C02=vulnerable`) derives the code as `VM-` + first 12 hex of an unsalted MD5 of the serial, so a player who buys two cards can forge the seeded flag card's code and redeem it. Redeeming emits `shop.giftcard_attempt`; the flag is in serial 1's message. Exploit test passes on the vulnerable build and fails on the fixed one; this is the only weak-crypto path in the shop (passwords stay on the strong hash).
- C01 Broken Access Control challenge (story 5.1 / T-19, FR-CHL-02, CWE-639): a seller order-detail API `GET /api/seller/orders/:orderNo` keyed by a sequential order number (migration 0003 adds `orders.order_no` + `orders.buyer_note`). One isolated, build-gated module (`challenges/c01-cross-store-order.mjs`): the fixed build (default) scopes the lookup to the caller's store (a foreign order is 404); the vulnerable build (`VM_CHALLENGE_C01=vulnerable`) drops the store check (IDOR) and emits `shop.cross_store_order_read` on a foreign read. The flag lives in a competitor order's `buyer_note`, which the support/finance order views no longer expose. Exploit test passes on the vulnerable build and fails on the fixed one. Introduces the shop's challenge-mode helper (`VM_CHALLENGE_<KEY>`, default fixed) threaded through `createApp`.
- Refunds, disputes, commissions and payouts (story 4.2 / T-18, FR-SHP-10): a new `money-service.mjs` and migration 0002. A refund is approved (by a seller for its own store up to `SELLER_REFUND_LIMIT_CENTS`, or by support/admin for any amount), rejected, or processed; processing reverses the platform commission in proportion (`round(commission × amount / paid)`) into the append-only `commission_reversals` ledger. Payouts accrue per store with `net = gross − commission(net of reversals) − refunds_deducted` (the seller bears refunds). Refunds carry an optional idempotency key so a retried approval/processing never pays out or reverses twice. The invariant throughout: an item's refunded total can never exceed the amount paid (the C04 weakness, epic 5, later bypasses this in an isolated path). Staff refund + payout-accrual screens and seller own-store refund approval. Shop tests 134 pass (+11).
- Seller flows (story 4.1 / T-17, FR-SHP-06): a new seller-side domain service (`seller-service.mjs`) and `/seller/...` screens over the existing T-06 schema. A customer registers a store (it starts `pending`), an admin approves it (T-15), and the seller then creates products, submits them for review (refused while the store is pending — "a pending seller cannot publish"), fulfils own-store order items (paid→processing→shipped→delivered, or cancel), edits the store profile, and promotes/removes store staff. Every action is scoped to the seller's own store via the RS-G matrix (`own_store`); no deliberate weaknesses (the C10/C11 seller-path challenges are later epics). Shop tests 123 pass (+15).
