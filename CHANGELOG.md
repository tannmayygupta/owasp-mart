The exploit-runner CI job already runs these self-tests, so a failing exploit blocks the release.
- C11 Mishandling of Exceptional Conditions challenge (story 7.3 / T-29, FR-CHL-12, CWE-636/755): KYC-gated seller registration `POST /sell/register` (migration 0008 adds `stores.approved_by`). The shop sends the tax id to a KYC provider; a malformed shape crashes it. The fixed (default) build fails closed (store stays pending); the vulnerable build (`VM_CHALLENGE_C11=vulnerable`) returns "verified" on any provider error and auto-approves the store with `approved_by=system:kyc-fallback`, and the Payouts page then shows the flag (shown only for a fallback-approved store). Events `kyc.result`, `store.approved`. This completes all 11 OWASP challenges (C01-C11). Exploit test passes on the vulnerable build and fails on the fixed one.
- C10 Server-Side Request Forgery challenge (story 7.2 / T-28, FR-CHL-11, CWE-918): the product editor's "Import image from URL" (`POST /seller/import-image`, `challenges/c10-ssrf-import.mjs`). The fixed (default) build resolves the host to an IP and refuses private/loopback/link-local addresses; the vulnerable build (`VM_CHALLENGE_C10=vulnerable`) uses a string blocklist of a few literal addresses, which a variant form (the decimal IP of loopback) evades, so the importer reaches the internal metadata service and the non-image response leaks the flag in its first 200 characters. http/https only (so `file://` cannot read local files); event `importer.fetch_attempt`. Exploit test passes on the vulnerable build and fails on the fixed one.
- C09 Logging/Alerting Failures challenge (story 7.1 / T-27, FR-CHL-10, CWE-778): the shop web login now writes every attempt to the `security_events` log and locks the account after 5 tries with an alert; a legacy mobile login `/m/api/v1/login` (`challenges/c09-logging-failures.mjs`) skips that pipeline on the vulnerable build (`VM_CHALLENGE_C09=vulnerable`) — no event, no lockout, no rate limit — so a slow brute force against the dormant support agent is invisible and never locks, and the obtained session reads the break-glass flag in the support case notes; the fixed build routes the legacy login through the same pipeline. Epic-challenges-c09-c11 incepted. The IF-4 `shop.security_event_written` platform event is deferred until the posted schema lists it (deferred-work). Exploit test passes on the vulnerable build and fails on the fixed one.
- C08 Software/Data Integrity Failures challenge (story 6.4 / T-26, FR-CHL-09, CWE-345): the payment webhook `POST /webhooks/payments` and a pending-order path `POST /api/orders/pending` (migration 0007 adds `payments.payment_ref` + `payments.verified`). The gateway signs events with an HMAC; the fixed (default) build always verifies it, while the vulnerable build (`VM_CHALLENGE_C08=vulnerable`) skips the check when `X-Gateway-Mode: sandbox` is present, so a player replays an unsigned event, turns their own order paid, and the response carries the sentinel `payment_ref` (the flag). A bypass-paid order is `verified=0` (not refundable, so it never feeds C04). Events `webhook.received`, `order.paid` (verified). Exploit test passes on the vulnerable build and fails on the fixed one; a signed event is accepted on both but never yields the flag.
- C07 Authentication Failures challenge (story 6.3 / T-25, FR-CHL-08, CWE-307/640): the shop's password-reset flow (migration 0006 adds `password_resets` + an internal `mailbox`) with `/auth/forgot`, `/auth/reset/confirm`, a finance settlement settings page (`/finance/settings/settlement`, the flag), and a test-only mailbox (`/test/mailbox`, VM_TEST). The fixed (default) build issues a 128-bit hashed token, answers generically, and kills the token after an attempt limit; the vulnerable build (`VM_CHALLENGE_C07=vulnerable`) issues a 4-digit code with no attempt limit and a response that reveals whether the account exists, so the finance account is taken over by brute force and its settlement flag read. Events `auth.reset_requested`, `auth.reset_confirm_batch`, `auth.password_reset_completed`. Exploit test passes on the vulnerable build and fails on the fixed one; the reset code is never returned by a route.

### Added (Sprint 3, Sahil, stream T)
- C06 Vulnerable Components challenge (story 6.2 / T-24, FR-CHL-07, CWE-1321): the import-service worker's product-preview merge. The fixed (default) build keeps the safe merge (drops `__proto__`/`constructor`/`prototype`); the vulnerable build (`VM_CHALLENGE_C06=vulnerable`) uses a naive recursive `unsafeMerge`, so a `__proto__` import patch pollutes the worker's prototype. Contained in the fresh per-job worker process (no network, no database), so there is no code execution and nothing to exfiltrate — the worker's `proto_check` reports `polluted` vs `clean`. Self-test drives `runJob` in both modes.
- C05 Security Misconfiguration challenge (story 6.1 / T-23, FR-CHL-06, CWE-489/209): a `challenges/c05-ops-console.mjs` mounting (before CSRF, anonymous) `GET /_ops/`, `GET /_ops/diagnostics` and a verbose `POST /api/cart`. The vulnerable build (`VM_CHALLENGE_C05=vulnerable`) serves the ops console and a hand-built synthetic diagnostics object whose `support_bridge_token` is the flag, and returns a stack trace naming an internal `_ops` file on broken JSON (events `ops.page_served`, `shop.verbose_error`); the fixed build 404s `/_ops/*` and returns a generic error with a correlation id. The diagnostics object is synthetic only — never env/db-url/secret — so it leaks no real data. Exploit test passes on the vulnerable build and fails on the fixed one. Epic-challenges-c05-c08 incepted.
- C04 Insecure Design challenge (story 5.4 / T-22, FR-CHL-05, CWE-840): a quick-refund path `POST /api/orders/:id/refunds` (migration 0005 adds `refund_ledger`, `goodwill_adjustment`, `sentinel`). The vulnerable build (`VM_CHALLENGE_C04=vulnerable`) checks only a per-request limit, so two below-limit refunds on one order push the refunded total past the amount paid, writing a `goodwill_adjustment` flag line and emitting `shop.refund_invariant_broken`; the fixed build routes through one shared order-level invariant (`money.orderRefundableRemaining`, counting item refunds + the quick ledger) and refuses the overshoot. `approveRefund` (T-18) now also enforces that order-level invariant, so every refund path shares it. Credit goes to the non-spendable `refund_ledger`. Exploit test passes on the vulnerable build and fails on the fixed one.
- C03 Injection challenge (story 5.3 / T-21, FR-CHL-04, CWE-89/79): two build-gated weaknesses. Part A — `GET /api/products/search` runs against a separate read-only catalog store (`challenges/c03a-catalog-search.mjs`); the vulnerable build concatenates the term so a `UNION SELECT … FROM ops_notes` reads the notes (a SQL error emits `shop.catalog_query_error`), the fixed build parameterises. Part B — a customer's ticket message is rendered on a new support-console ticket-detail page (`challenges/c03b-ticket-xss.mjs`); the vulnerable build renders it as raw HTML (stored XSS), the fixed build escapes it, and storing a message with a tag emits `shop.ticket_markup_stored`. Exploit tests pass on the vulnerable builds and fail on the fixed. The injection cannot reach users/orders (separate store). The live part-B bot-token-exfil loop is deferred to the headless-bot work (S-5/H-44), recorded in deferred-work.
- C02 Cryptographic Failures challenge (story 5.2 / T-20, FR-CHL-03, CWE-328): a gift-card wallet (migration 0004 adds `gift_cards` + a non-spendable `promo_credit` ledger) with `POST /api/wallet/buy` and `POST /api/wallet/redeem`. One isolated module (`challenges/c02-gift-card-codes.mjs`): the fixed build (default) issues random CSPRNG codes and stores only a keyed HMAC; the vulnerable build (`VM_CHALLENGE_C02=vulnerable`) derives the code as `VM-` + first 12 hex of an unsalted MD5 of the serial, so a player who buys two cards can forge the seeded flag card's code and redeem it. Redeeming emits `shop.giftcard_attempt`; the flag is in serial 1's message. Exploit test passes on the vulnerable build and fails on the fixed one; this is the only weak-crypto path in the shop (passwords stay on the strong hash).
- C01 Broken Access Control challenge (story 5.1 / T-19, FR-CHL-02, CWE-639): a seller order-detail API `GET /api/seller/orders/:orderNo` keyed by a sequential order number (migration 0003 adds `orders.order_no` + `orders.buyer_note`). One isolated, build-gated module (`challenges/c01-cross-store-order.mjs`): the fixed build (default) scopes the lookup to the caller's store (a foreign order is 404); the vulnerable build (`VM_CHALLENGE_C01=vulnerable`) drops the store check (IDOR) and emits `shop.cross_store_order_read` on a foreign read. The flag lives in a competitor order's `buyer_note`, which the support/finance order views no longer expose. Exploit test passes on the vulnerable build and fails on the fixed one. Introduces the shop's challenge-mode helper (`VM_CHALLENGE_<KEY>`, default fixed) threaded through `createApp`.
- Refunds, disputes, commissions and payouts (story 4.2 / T-18, FR-SHP-10): a new `money-service.mjs` and migration 0002. A refund is approved (by a seller for its own store up to `SELLER_REFUND_LIMIT_CENTS`, or by support/admin for any amount), rejected, or processed; processing reverses the platform commission in proportion (`round(commission × amount / paid)`) into the append-only `commission_reversals` ledger. Payouts accrue per store with `net = gross − commission(net of reversals) − refunds_deducted` (the seller bears refunds). Refunds carry an optional idempotency key so a retried approval/processing never pays out or reverses twice. The invariant throughout: an item's refunded total can never exceed the amount paid (the C04 weakness, epic 5, later bypasses this in an isolated path). Staff refund + payout-accrual screens and seller own-store refund approval. Shop tests 134 pass (+11).
- Seller flows (story 4.1 / T-17, FR-SHP-06): a new seller-side domain service (`seller-service.mjs`) and `/seller/...` screens over the existing T-06 schema. A customer registers a store (it starts `pending`), an admin approves it (T-15), and the seller then creates products, submits them for review (refused while the store is pending — "a pending seller cannot publish"), fulfils own-store order items (paid→processing→shipped→delivered, or cancel), edits the store profile, and promotes/removes store staff. Every action is scoped to the seller's own store via the RS-G matrix (`own_store`); no deliberate weaknesses (the C10/C11 seller-path challenges are later epics). Shop tests 123 pass (+15).
