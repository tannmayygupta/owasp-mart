# Scenario matrix with evidence, 2026-10-21

Work package G, refreshed on 2026-10-21 after packages A to E were merged. Every one of the 145 scenarios of [2026-10-21-role-scenarios.md](2026-10-21-role-scenarios.md) was exercised against the code of `origin/main` (first on db3721b, then on cd9610e; the scenarios that were missing or partial were tested again) through the real routes and services of the combined world (`apps/api/tests/scenario_support.py`: the real lab runtime on the fake instance host, the real company, invite, consent, deletion, export, break-glass and admin services on SQLite). A scenario is `VERIFIED` only when a passing test named in the table proves it. `test_scenario_matrix.py` fails when a row names a test that does not exist, when a `VERIFIED` row has no test, or when an id is missing.

Status words: **VERIFIED** (works on main, proved by the named test), **PARTIAL** (part works and is proved, the note says what is missing and who owns it), **MISSING-OWNED-BY-<letter>** (the behaviour does not exist on main; the letter is the work package that builds it: A attempt lifecycle, quotas and template settings; B company deletion, colleagues and mail; C deployment; D shop and challenges; E learner and candidate web; F recruiter and admin web; H what no package had, assigned on 2026-10-21), **MISSING-UNOWNED** (not built and no package has it; none is left), **EXTERNAL** (needs the deployed stack, a browser audit or a host, not an API test).

Tests assert behaviour that is correct on main today, not internals, so they keep passing when package F merges. Where a test proves only part of a scenario the note says which part.

## Findings made while testing

- **Concurrent identical flag pastes journal the capture more than once** (score is right): `test_scenarios_cross.py::test_xc2b_the_milestone_is_journalled_once_when_the_same_flag_is_pasted_at_once` (xfail until fixed). The flag path is touched by package A.
- **The combined world cannot model concurrent HTTP requests**: its test database is one shared SQLite connection (`InterfaceError` under threads). Thread tests therefore call the lab runtime; the invite and company races are proved on Postgres by `test_assessments_postgres.py` and `test_invite_acceptance_postgres.py` (they skip without a database).
- **Suspending a company does not end its recruiters' sessions** (only deleting does); the company is simply unable to invite (`test_a03_...`). **Deleting a company leaves its running attempts running** (`test_a04_r33_x09_...`).
- **An unverified account is refused at sign-in** (403), earlier than the audit's 409 at accept (C-05).
- **The deletion request, force-stop, the retention jobs and the new open-attempts list read the SQL attempt and instance tables**, which the in-memory lab store of this world does not fill; the tests mirror the rows (`mirror()` in `test_scenarios_refresh.py`).
- **A start that fails leaves the attempt `ready` and destroys the instance**, so an operator cannot tell a failed start from a candidate who has not pressed Start; `listOpenAttempts` shows both as `waiting` (A-27).
- **Still open from the first run:** the duplicate `milestone_reached` line for concurrent identical pastes (xfail `test_xc2b_...` still fails on main). Three of the four admin settings in A-10 (`instance_idle_minutes`, `instance_max_minutes`, `flag_submit_per_minute`) are wired as of 2026-10-23; `hints_enabled_default` stays deliberately deferred (see A-10's row: the blast radius across every `AttemptRecord`/`Rules` construction path in the test suite needs its own audit first).
- **Not mine, seen on the way:** `node --test scripts/check-deployed-compose.test.mjs` has one failing test on this Windows checkout (`fails when: no http redirect`).
