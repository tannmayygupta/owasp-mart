# Runbook: the live demo deployment (platform on vm-p, lab on vm-i)

Story: production readiness 9.5 (stream L). This is how the deployed system of the demo is made and checked. Every step is a command of the repository; secrets go as files over ssh and are never printed or committed. The two hosts and their addresses come from `terraform output` in `infra/terraform/aws` (open the shell with `$env:AWS_PROFILE = "vulnmart"`); the allowed source address in the security group must be your current address (`ssh_source_cidrs` in `terraform.tfvars`, then `terraform apply`).

**Cost:** vm-i and vm-p run until you stop them (`vm_i_running = false`, `terraform apply`).

## What runs where
- **vm-p** (`infra/deploy/platform.compose.yaml`, project `vulnmart-platform`): Postgres 18, Valkey (password, append-only file on the volume `valkey-data`, policy `volatile-lru`), the API with the lab runtime (`VULNMART_LAB_RUNTIME=1`, state in Postgres) and the retention scheduler (`VULNMART_SCHEDULER_ENABLED=true`), the mail worker (Brevo), the dashboards (`web`, image `vulnmart-web:prod`: recruiter, candidate, admin, invite, consent and account pages), and Caddy. Mailpit is a profile (`mail-catcher`) that is off unless you deploy with `--allow-mail-catcher`. Caddy serves the site on 443 (the lego certificate of the platform name) with three kinds of answer: `/api/*` and `/healthz` to the API (the origin secret is added by Caddy), the dashboards' paths (list `@dashboards` in `infra/deploy/Caddyfile.platform`, the page folders of `apps/web/app`) to `web`, which sets its own per-request nonce CSP, and everything else to the demo console `apps/lab-console` under the strict CSP. Port 80 only redirects to https. A private TLS listener on `<vm-p private address>:9444` carries only `POST /internal/v1/events`, `POST /internal/v1/orch/state` and `GET /internal/v1/orch/desired` (the wanted instances, H-123) for vm-i. `node scripts/check-deployed-compose.mjs` fails when any of this drifts (it runs in CI).
- **vm-i** (`infra/compose/compose.yaml`, profile `lab`): the Docker socket proxy, the edge (Caddy 443 with the wildcard certificate of the labs zone and the gate), and the orchestrator (mutual TLS on `<vm-i private address>:9443`). Instances are created by the orchestrator from the images in `images.json` (digest-pinned references to a local registry on 127.0.0.1:5000 of vm-i).
- Instance contents: the **real shop** (`apps/shop`, distroless, with a seeded snapshot baked into the image) started by its own `inject` script as the one-shot injector (IF-6 section 5; handoff H-26), the **product** sidecar, import service, mock services and bot controller. Only the volume keeper still uses the stub image (it only holds the volumes). An instance now declares 832 MB (shop 192, sidecar 160, injector 128, import 64, mock 96, bot 128, keeper 64), so `--capacity-mb 5600` admits 6 instances. Challenges are exploitable in an instance exactly when their flag was planted (the shop reads the flags file).

## Steps (from the repository root, on your PC)
1. `node scripts/deploy-secrets.mjs --out %USERPROFILE%\.vulnmart-deploy\prod --vmi-ip <vm-i private> --vmp-ip <vm-p private> --days 90` (once; `--force` replaces everything, which also means new certificates everywhere).
2. `node scripts/live-deploy.mjs build` (eight images, a few minutes), then `ship-i` and `ship-p` (they `docker save`, copy and `docker load`).
3. `node scripts/live-deploy.mjs lab --secrets <folder> --zone <labs zone>` stages the secrets on vm-i (owner 65532, mode 400), starts a local registry, pushes the images, writes `images.json` from the digests it got and starts the lab stack.
4. `node scripts/live-deploy.mjs platform --secrets <folder> --zone <labs zone> --platform-host <platform name>` does the same on vm-p (it also creates a 2 GB swap file; vm-p has 2 GB of memory).
   **Before this step** (once): the real mail key, see "Real e-mail" below. Without it the command stops. To run knowingly without real mail add `--allow-mail-catcher`.
   The same command is the dashboards deploy: `ship-p` ships `vulnmart-web:prod` (built from `apps/web/Dockerfile.prod`, context `apps/web`) beside the API image and the compose file starts `web` and routes its pages. To update only the dashboards after a change in `apps/web`: `node scripts/live-deploy.mjs build && node scripts/live-deploy.mjs ship-p && node scripts/live-deploy.mjs platform --secrets <folder> --zone <labs zone> --platform-host <platform name>`.
5. `node scripts/live-deploy.mjs status`, then `node scripts/verify-deployed.mjs --base https://<platform name> --platform-env <the .env that was staged>`: every dashboards page must answer from the dashboards app with a nonce CSP, `http` must redirect to `https`, and no operation of the contract may answer 404.
6. `node scripts/e2e-live.mjs --base https://<platform name> --mailpit-ssh ubuntu@<vm-p address> --json docs/assets/<folder>/e2e.json` (one learner start to finish) and with `--load N` for the load check.
7. `node scripts/vmi-audit.mjs --from <folder of the saved outputs>` for the isolation audit; `node scripts/backup.mjs` for the backup and restore test (docs/runbooks/backup-restore.md).

## Real e-mail (Brevo)
The API and the worker send mail through the Brevo adapter. The key is an external credential: **you** create it in the Brevo account (SMTP and API, "API keys", a key with the sending permission) and put it in the secrets folder, never in the repository and never in a command line or a chat. The sender address is `no-reply@<platform name>` (`VULNMART_EMAIL_SENDER_ADDRESS`); Brevo must have that domain or address verified as a sender, otherwise it refuses every send. On your PC (PowerShell; the folder is the one of step 1):
```
$secrets = "$env:USERPROFILE\.vulnmart-deploy\prod\keys"
$key = Read-Host -AsSecureString "Brevo API key"
[IO.File]::WriteAllText("$secrets\brevo_api_key", [Net.NetworkCredential]::new('', $key).Password)
```
Then run step 4 again. The deploy stages the file as `/opt/vulnmart/platform/secrets/brevo_api_key` (owner 65532, mode 400) and writes `VULNMART_EMAIL_PROVIDER=brevo` and `VULNMART_ALLOW_MAIL_CATCHER=false` into the `.env`. Production refuses to start with the catcher unless `VULNMART_ALLOW_MAIL_CATCHER=true` was set knowingly (`settings.py`, `check_mail_for_environment`), and with provider `brevo` and an empty or missing key file. `verify-deployed.mjs --platform-env` fails when the staged `.env` names the catcher.

## The retention scheduler
Turned on in the deployed stack (`VULNMART_SCHEDULER_ENABLED: "true"` on the `api` service, ADR 0054 and 0057): invite expiry, candidate and learner retention, deletion requests after their undo window, the daily audit anchor (written to `/opt/vulnmart/platform/anchors/audit-anchor.log`; ship that file off the machine), log and token purges. Every job runs under a lease in `job_runs` and acts only on rows past their retention or undo window; a job that fails is recorded and reported to the admins, and the others still run. Proof on real tables with the application role: `apps/api/tests/test_retention_postgres.py::test_the_first_pass_of_a_fresh_deployment_deletes_nothing_it_must_keep` (and the 106 other retention, deletion and invite tests, run against Postgres in the CI job `api`). To turn it off: set the variable to `"false"` and `docker compose up -d api`; nothing is deleted while it is off. The admin jobs screen shows each job's last run.

## Stopping and repairing
`node scripts/live-deploy.mjs down-lab | down-platform`. A command can be run again at any time: files are replaced, containers are recreated only when they changed.

## For people who must use the live site (a demonstration)

- **Link:** https://tanmay-platform-prod.duckdns.org/ (the console; ports 80 and 443 are open to everybody since 2026-10-19; SSH only to the developer's address, refresh it with `node scripts/allow-my-ip.mjs`).
- **Accounts:** with a Brevo key staged (above) a sign-up mail reaches the person. Only a deploy with `--allow-mail-catcher` sends to Mailpit on vm-p (private), where a person who signs up alone never receives it. Then make confirmed demo accounts with `node scripts/demo-accounts.mjs --base https://tanmay-platform-prod.duckdns.org --mailpit-ssh ubuntu@<vm-p address> --out <file outside the repository> --count 5 --prefix demo`. It prints the e-mail addresses (`demoN@vulnmart.example`) and writes the passwords to the file (mode 0600), never to the screen or the repository. The developer holds the file made on 2026-10-19 (`C:\Users\tanma\.vulnmart-deploy\prod\demo-accounts.txt`).
- **What a visitor does:** sign in, press Start, wait a few seconds for the instance, press Open (the console opens the shop in a new tab through the gate), attack the shop, paste or let the sidecar credit a flag, see the score, press Submit. The deployed journey `scripts/e2e-live.mjs` does exactly this through the API (31 checks).
- **Deploying the console:** `live-deploy.mjs platform` replaces the CONTENT of `console/` and `catalog/` (never the folder): a folder that is deleted and recreated leaves a running container with an empty, stale mount (this made the site answer 404 at the root until Caddy was restarted on 2026-10-19; the journey now checks the root page).
