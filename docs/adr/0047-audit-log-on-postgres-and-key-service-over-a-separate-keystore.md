# 0047. The audit log on Postgres with pseudonymised subjects, and the key service over a separate keystore database

- **Status:** Proposed (the builder's design for the developer to confirm; the requirements and ADR 0008, 0009 fix the outcome; OI-28 was answered by the developer on 2026-10-18: self-hosted on VM-P)
- **Date:** 2026-10-18
- **Deciders:** Claude Code (design); the developer to confirm
- **Requirements:** FR-PRV-10, FR-PRV-12, NFR-SEC-02, OI-28, D-25, D-35, spike S-10

## Context
The IF-9 `AuditPort` and `KeyPort` existed only as in-memory fakes (story P-05). FR-PRV-10 asks for a pseudonymised, hash-chained, append-only log kept 12 months; FR-PRV-12 for a per-attempt key that can be deleted so that backups cannot restore the data. Architecture 04 sections 4 and 5 and ADRs 0008 and 0009 give the outline (advisory lock, `audit_writer` and `audit_purger` roles, a daily anchor outside the database, wrapped DEKs in a separate `vm_keystore` database, latest-only keystore snapshot). They leave open how the log is written relative to the caller's transaction, where pseudonyms are applied, how the keystore database gets created, what the anchor is, and how the key service stays consistent between processes.

## Options considered
1. **Audit write:** inside the caller's transaction (needs a request-scoped session that does not exist yet) / in a transaction of its own, committed before the caller's.
2. **Pseudonyms:** every module maps ids itself / one adapter in front of the port.
3. **Subject mapping and deletion:** a foreign key from `subject_map` to `users` with a cascade / no foreign key and an explicit delete.
4. **Row storage:** `details` as JSONB / as the canonical JSON text that the hash covers.
5. **Roles:** separate `audit_writer` and `audit_purger` roles now / the application role with SELECT and INSERT only, the purge path left to story P-24.
6. **Anchor:** a signed commit to a private repository plus an email (the ADR 0008 proposal) / a signed line in a table and a file on VM-P that an operator ships off the machine.
7. **Keystore creation:** the compose initdb script / a second Alembic history / the migrate job, idempotently.
8. **DEK access:** cache unwrapped keys in the process / read and unwrap on every call.

## Decision
- **Audit write:** `DbAuditPort` opens a transaction of its own, takes `pg_advisory_xact_lock` on the chain, reads the head, writes the next entry and commits, before the caller commits. Consequence: an action that is then rolled back still leaves its entry (a conservative "attempted"), and an entry is never missing for an action that happened. Its sessions come from a small pool of their own so that callers holding connections cannot starve it.
- **Hash:** the same rule as the in-memory port, `SHA-256(prev_hash || canonical JSON of {seq, at, actor, action, subject, details})`, so the two ports verify with the same function. `at` is whole seconds UTC. `details` is stored as the canonical JSON text.
- **Refused content:** keys named like a secret (password, token, secret, key, cookie, authorization, otp, credential) and values that look like a token (40 or more URL-safe characters that are not a hash) raise ValueError, so a caller fails in its own tests instead of writing a secret into a log that cannot be edited. Details are limited to 4 KiB; actions are dotted lower-case names.
- **Pseudonyms:** `PseudonymisingAudit` wraps the port and replaces every user id in actor, subject and details by the person's `s-...` pseudonym (`subject_map`, made on first use, race safe). `SubjectService.forget(user_id)` deletes the mapping: the entries stay and identify nobody. `subject_map` has no foreign key to `users` because a pseudonym is needed while the user row is still uncommitted in another transaction (an admin being created).
- **Privileges:** the application role has SELECT and INSERT on `audit_log`, `audit_checkpoint` and `audit_anchor` (and SELECT, INSERT, DELETE on `subject_map`), nothing else. The separate `audit_writer` role of the architecture is not created: the writer must read the head, so it needs SELECT, and the application is the only writer. The purge (12 months, with a checkpoint written first) needs a privileged path and is story P-24; verification already starts from the latest checkpoint.
- **Anchor:** `AuditAnchors.anchor()` verifies the whole chain, then publishes one line per day, `date seq head-hash signature`, to a sink outside the database (`FileAnchorSink`, a file on VM-P, OI-28) and records it in `audit_anchor`; a second call on the same day changes nothing and a broken chain anchors nothing. `check()` compares lines kept elsewhere with the chain and detects a forged line, a changed entry and a log cut short. The signature is a keyed hash under a key derived from the field secret. The signed commit to a repository and the email to admins are not built.
- **Keystore:** wrapped DEKs live in database `vm_keystore` (tables `deks`, `shredded`), reached only by role `vulnmart_keys` (the application role cannot connect), which has SELECT, INSERT, DELETE on `deks`, UPDATE on `kek_version`, `nonce` and `wrapped` only (a KEK rotation rewraps), and SELECT, INSERT on `shredded`. `python -m vulnmart.kernel.migrate` creates database, role and tables idempotently after the Alembic history, so it works on existing volumes (a compose initdb script runs only on a fresh volume).
- **Keys:** a DEK is 256 random bits, wrapped with AES-256-GCM under the highest KEK version (the attempt id and DEK id are the associated data); evidence is sealed with AES-256-GCM under the DEK (the attempt id and the caller's data are the associated data). `shred` deletes the wrapped key and writes the attempt id to `shredded` in one transaction under a per-attempt advisory lock, so a create that races with a shred never brings a key back. Nothing is cached: every call reads and unwraps, so a shred in one process is seen at once by every other, at the price of one primary-key read per call.
- **Masters:** the event, flag and owner keys are three different files of at least 32 bytes; the service refuses two equal values. The derivations are the pure functions already in `ports/keys.py`. The port has no flag key version argument yet (handoff H-137).
- **What is logged now:** logins, failed logins (with a reason, never the address or password) and logouts (`SessionService`), plus the entries that already existed (roles, admins, second factor, consent). Everything else of FR-PRV-10's list is written by the story that creates the event.

## Consequences
- A crash between the audit commit and the caller's commit leaves an entry for an action that did not happen; for a security log that is the safe direction. An audit database outage fails the action that needed the entry (login, role change), by design.
- Every failed login writes a row; the rate limits bound the volume, but an attacker with many addresses can still grow the log (12-month retention, story P-24).
- Losing the KEK, or the keystore without a copy, makes every sealed value unreadable (ADR 0009). The snapshot procedure after a shred is an operator step until a deployment story automates it.
- `ConsentRecord.user_id`, `email_outbox.to_user_id` and other tables still hold raw user ids: the pseudonym protects the audit log only. Pseudonymising the others on deletion is story P-25 (handoff H-136).
- The seed-admin command still writes its entry to an in-memory port, not to this log (it runs outside the API process).

## Evidence
- `test_audit_log.py` (chain, tampering of each column, removal, whole-chain rewrite found only by the anchor, checkpoint, refused secrets, anchors, pseudonyms), `test_audit_postgres.py` (privileges as the application role, 8 threads writing 200 entries with no gap or fork, a rolled-back caller, the pseudonym race, checkpoint and anchor on Postgres, migration down and up), `test_keys.py` (KEK ring, wrapping, sealing, shred semantics identical to the fake, rotation and rewrap, derived keys), `test_keys_postgres.py` (the keystore role's limits, the application role cannot connect, creating and shredding races, a shred seen at once by another process, the restore of a copy of the data taken before a shred leaves only the shredded attempt unreadable, the migrate job), `test_session_audit.py`.
- Real stack: a login through the proxy leaves entries under a pseudonym, no user id or address in the table, the chain verifies and anchors, the API role is refused UPDATE, DELETE and TRUNCATE, a key is created, used and shredded in `vm_keystore`, and the application's role cannot connect to it.
- The restore test uses a copy of the data database taken before the shred, not a restore from backup files on object storage; nothing was run on the VMs.
- OWASP ASVS 5.0 (the key management and logging chapters), NIST SP 800-57 and SP 800-38D (GCM nonce handling: random 96-bit nonces are used; the volume per key is far below the limit): **not re-read in this story.**
