# 0071. Template settings, quotas and the attempt lifecycle in the lab

- **Status:** Accepted (the leader instructed the audits of 2026-10-21 to be implemented; confirmed by the leader on 2026-10-21)
- **Date:** 2026-10-21
- **Deciders:** the leader (Tanmay), with Claude Code
- **Requirements:** FR-HNT-02, FR-SCR-03, FR-ASM-01, FR-ASM-03, FR-ASM-05, FR-ADM-05, FR-INS-06, FR-SES-07, FR-SES-10, OI-21
- **Research:** the two audits of 2026-10-21 (`docs/audit/2026-10-21-wiring-audit.md`, `docs/audit/2026-10-21-role-scenarios.md`); fixed-window per-account limits are the existing platform pattern (`kernel/ratelimit.py`); a reserved slice of capacity for the paid or priority workload is the usual admission-control pattern (Kubernetes ResourceQuota and priority classes, cloud instance quotas), and `503` with `Retry-After` is the RFC 9110 answer for "no capacity now" (a `429` means the caller sent too much).

## Context
The wiring audit found the template's settings, the admin's quotas and the invite state ignored by the lab, the invite expiring under a running assessment, a revoked invite leaving a startable attempt, a full orchestrator reported as "too many tries", and a deployed API able to start on fakes. The role-scenario audit added the missing recruiter cancel, the missing withdrawal consent record and the unseparated practice and assessment lists.

## Decisions
- **Rules carry the template.** `Rules` (py-attempts) gets `hints_mode`, `hint_cost_pct`, `challenge_keys`, `flag_submissions_per_minute` and `writeup_required`, validated strictly; `attempt_rules` copies them from the invite's rules (they reach the attempt through `rules=view.rules` at consent). A regression test goes invite -> accept -> consent -> stored attempt.
- **Subset.** An attempt's challenges are the template's subset, or all eleven when it is empty or the attempt is a learner's. `LabRuntime.keys_for` is the one place; list, hints, flags, score, report, the cohort view and the live score use it. A flag or hint outside the subset is `ATT-CHALLENGE-NOT-FOUND`. The score is out of 1000 over the subset's weights (the library's `Catalogue` with the subset).
- **Hints.** A candidate has hints only when the template says `on` (route 404 `ATT-HINTS-DISABLED`, and the runtime refuses too). Level L costs `hint_cost_pct x L` percent of the challenge's points, at most 100 (10 gives the 10, 20, 30 of PRD Appendix A; the template default when on, 20, gives 20, 40, 60). The same figure is shown by `listHints` and taken from the score. A learner's hints are free.
- **Flags per minute.** `FlagSubmitService` counts the pastes of an attempt in the last 60 seconds against the template's number (default 10); the answer is the existing `ATT-FLAG-RATE-LIMITED` with `Retry-After`. The wrong-answer limit (5 in 10 minutes per challenge) stays.
- **Invite lifecycle.** `startAttempt` asks the invite first (`AssessmentService.start_gate`): `consented` becomes `started`, `started` stays, anything else (revoked, expired, declined, cancelled) is 409 and cancels a `ready` attempt. `_refresh` never expires a `started` invite (so the recruiter's report link and the candidate's page stay). `revoke` and the scheduler's `expire_due` cancel the `ready` attempt behind the invite. A repeat invite after a closed one takes the next generation, so the consent creates an attempt under the key `<template>~N` and the attempt id the invite gave out is the attempt that exists. Cancellation of the attempt is best effort and logged; the start gate is the guarantee.
- **Quotas.** `LabRuntime.check_quota` runs before an instance is asked of the orchestrator (and before a new learner run exists, so a refused start leaves nothing behind). The user limit counts per mode (a practice run and an assessment can run together; the user limit is the admin's `quotas` row, default 1); the company cap counts the company's assessment instances; the platform cap counts everything, and `instance_assessment_reserve` (default 2) places of it are only for assessments, so learners cannot block a candidate's Start. A user or company limit is 409 `INST-QUOTA-REACHED`; a full platform is 503. The admin's change applies to the next request. We did not build "an assessment Start stops an idle practice instance"; the reserve gives the same priority without destroying a learner's work.
- **Capacity answer.** The orchestrator's `Busy` and the platform cap are 503 `INST-NO-CAPACITY` with `Retry-After: 15`, a new IF-8 code (registry 2.0.0; the rules engine treats any change of the registry file as breaking, so the major number is raised, the same reading as IF-2 2.0.0). It was 429 `REQ-RATE-LIMITED`, which blamed the user. `ORCH-BUSY` is not used because ORCH codes never reach a browser.
- **Rate limits** on the costly authenticated routes are per account and per hour, settings an admin can change: instance request and candidate Start (`rate_instance_start_per_user_per_hour`), ticket (`..._open_...`), stop and reset (`..._stop_...`), release, cancel and integrity decision (`rate_review_action_per_user_per_hour`). They count before the state checks, so a script cannot probe by looping. A limiter outage refuses the request (the platform's existing fail-closed rule).
- **Recruiter cancel (FR-SES-07).** `cancelAttempt` (IF-2 2.2.0): the recruiter of the owning company cancels a `ready` or `running` company attempt; the engine destroys the instance and records who and why (`recruiter`); the candidate sees `cancelled` in `getAttempt`. The mail to the candidate belongs to the notification work: it reads the attempt-state domain event (`to: cancelled`) that the engine already emits, and the lab writes a log line.
- **Withdrawal.** The withdraw route writes the minimal `withdrawn` consent record (`ConsentService.record_withdrawal`, append-only, once per attempt) after the withdrawal stands; a failure to write it is logged and never blocks the withdrawal, and repeating the call writes it. Undo keeps the attempt withdrawn (D-91): to take the assessment after all, the recruiter re-invites, which gives a fresh attempt. The invite itself is not moved by a withdrawal; the recruiter's re-invite and the invite expiry deal with it.
- **Learner and candidate separation.** Authorization is by attempt ownership and `org_id` (a recruiter reads only attempts of their own company; practice attempts are the owner's alone), proved by a route test where a recruiter of the inviting company gets 404 on every route of the invited person's practice attempt. `listMyAttempts` stays one list with `mode` on each item (changing IF-1 for a filter parameter was not needed); the lab console now shows practice attempts only. A learner's rules use `activity_check_mode = "flag"`, because no reviewer exists for practice and a held capture could never be released.
- **Fail closed.** `check_deployable` (run when the lab is mounted) refuses, for `VULNMART_ENV` staging or production, a fake instance host, a non-persistent attempt store and missing quotas, naming each problem; the explicit dev escape is `VULNMART_ALLOW_FAKE_LAB=1`. A mistyped orchestrator variable therefore stops the API instead of running on a fake.

## Consequences
Recruiters' settings finally apply; candidates get hints only when the template says so. The write-up flag and the technique label are stored but there is no candidate write-up feature (open). The first-hour limits are placeholders (OI-25 style) to be tuned. The quota counts live instances by asking the orchestrator for each (at most a few tens). IF-8 is now 2.0.0 and IF-2 2.2.0; the COMPAT rows are the leader's to close.

## Alternatives
Counting the user limit across both modes (the audit's proposal) would stop a candidate from practising while an assessment runs, which the role scenarios call a defect; the reserve covers the priority. A new `REQ-UNAVAILABLE` code was an option; `INST-NO-CAPACITY` names the condition and stays in the instance family.
