# 0052. Live updates: the event outbox in Postgres, a relay into one Valkey stream per audience, ids from one counter, and the hub in the API process

- **Status:** Proposed (the builder's design for the developer to confirm; ADR 0006 chose the outline, the requirements fix the outcome)
- **Date:** 2026-10-18
- **Deciders:** Claude Code (design); the developer to confirm
- **Requirements:** FR-LIV-01, FR-LIV-02, FR-LIV-04, FR-LIV-05, FR-LIV-06, NFR-PRF-03, ADR 0006, contract IF-3 (`contracts/domain-events/`), IF-1 (`/api/v1/live`, `/api/v1/live/snapshot`)
- **Handoffs:** H-142

## Context
ADR 0006 chose: a domain-event outbox table in Postgres, relayed to Valkey Streams whose ids become the SSE ids, a hub that reads with blocking reads, audiences from the session, a replay buffer trimmed by age or length, `stream.resync` when an id is missing or too old. It left the details open: how a relay that can die half way avoids a second copy of an event, how a reconnect is judged when the entries it needs may have been trimmed or Valkey may have been reset, what ids look like when one user reads several streams, how a slow or dead client is handled, and where the hub runs. IF-3 and IF-1 already fix the wire (id, event name, data, heartbeat comment, headers, `Last-Event-ID`, the three resync reasons).

## Options considered
1. **Where the hub runs:** a container of its own (ADR 0006's wording) / inside the API process.
2. **What the relay does when it dies between the append and the mark:** accept duplicates and let the client drop them / make the append idempotent.
3. **Ids across streams:** the ids Valkey gives each stream (they can repeat across streams: `<ms>-0` in two streams) / one id space for all streams.
4. **Telling that entries were trimmed:** compare with the oldest entry of a stream / remember what each trim removed.
5. **Telling that Valkey was reset:** nothing can be known afterwards / keep two facts with the entries that a reset takes along.
6. **A client that does not read:** let the write block / a bounded queue between the Valkey read and the response, and drop the connection when the queue stays full.
7. **Who resolves the audiences:** the publisher (it would have to know the user and company) / the relay, from the attempt.

## Decision
- **Outbox:** table `domain_events` (migration 0013; owner `live`, already in `table-owners.yaml`). A publisher (`DbEventPublisher`, behind `OutboxPort.publish`) adds one row with the IF-3 event exactly as the browser will read it, in the transaction of its cause when it is given that session, in a transaction of its own otherwise. The same `check_event` as the in-memory outbox refuses anything IF-3 does not allow, so both accept exactly the same events (a test runs the examples of the contract through it). `build_ports` now gives every process with a database a durable event port (`LiveOutbox`); emails still go to the stand-in until the mail outbox has a request session (P-09). The application role may add, read, delete, and update only `published_at`, `relay_attempts` and `dropped`: it cannot rewrite what an event says.
- **Relay** (`live/relay.py`, runs in the worker process every 250 ms, setting `live_relay_interval_seconds`): one relay at a time (a Postgres transaction advisory lock, so a second relay returns at once), takes the unpublished rows in outbox order, resolves each event's audiences from its attempt (`AudienceResolver` reads the lab's `attempts` table: owner and, for a candidate attempt, company; the kinds per type and mode come from `audiences.json` through `audiences_for`), appends to the stream of each and marks the row. A row whose attempt is not found waits (the rows behind it wait too, to keep the order) and is dropped after 20 passes, logged by id and type only. Learner practice has no company audience in the table, so it can never reach a company.
- **Idempotent append:** the store remembers the newest outbox row appended to each stream and refuses an older or equal one, in the same Lua script as the append, so a relay that starts over after a crash never makes a second entry. (A test kills a relay after its second append.)
- **Ids from one counter:** an id is `<ms>-<seq>`, the milliseconds the later of the clock and the newest id given out, the sequence one Valkey counter for all streams. An id is unique over every stream, ids grow in append order, and a user who reads several streams (own, company, admin) gets one ordered sequence of ids. The same event in two audiences has two ids.
- **Trimming** keeps 1000 entries and one hour per stream (placeholders, OI-25), exactly, in the same script; each trim records the id of the newest entry it removed. **Facts** kept with the entries: `latest` (the newest id given out) and `barrier` (the first id since the store was empty). A reconnect is judged by them: not an id, or newer than `latest` -> `id_unknown`; older than `barrier`, or no facts at all -> `buffer_reset`; older than what a trim removed from one of the user's streams -> `id_too_old`; otherwise replayed. One `stream.resync` without an id, then the connection ends (IF-3). A client that held exactly the newest id before a reset is told to resync too (the data that would show it is gone with the reset); the cost is one snapshot read.
- **The hub** (`live/hub.py`, `live/api.py`) runs in the API process (the contract's wording allowed a second container; one process is simpler to run and to test, and the hub holds no state a restart loses). The streams of a connection come from the session: the caller's own user stream, their company's stream for a recruiter acting for one, the admin stream for an admin; nothing the client sends picks a stream. A connection without `Last-Event-ID` starts at the newest id of each stream. A heartbeat comment every 15 s while nothing arrives, an immediate `: stream open` comment, `Cache-Control: private, no-store`, `X-Accel-Buffering: no`. Every 30 s the session is resolved again and the connection ends if it is gone or its streams changed; every connection ends after 15 minutes (the browser reconnects and resumes with `Last-Event-ID`). A bounded queue sits between the Valkey read and the response; a client that does not read for 10 s is dropped. At most 6 streams per user and 2000 per process (429 with `Retry-After`), and 600 connection attempts an hour per user. All of these are placeholders in `HubConfig` (OI-25).
- **Snapshot:** `GET /api/v1/live/snapshot` is the caller's own attempts and instances in the shapes of the IF-3 events, read from the lab runtime in the same process (empty without one). A recruiter has no attempts of their own: the company's attempts are a dashboard read (P-27).
- **Not served:** `POST /api/v1/live/ticket` stays pending spike S-14 (plan B of ADR 0006).

## Consequences
- Events are durable from the moment their cause commits; Valkey holds only the replay buffer and a loss costs a resync. A Postgres outage stops new events reaching the streams; the hub and the buffer keep working.
- The latency from a committed row to a frame is the relay interval (250 ms) plus the blocking read; measured on the local stack in the stack test (see the dev-log). The numeric target of NFR-PRF-03 is still open until spike S-2.
- The hub's counters are per process: with several API processes the per-user cap is per process.
- A deleted or purged attempt's events that are still unpublished are dropped after 20 passes; ones already in a stream stay until trimmed (an hour at most).
- The stream carries ids and states only (IF-3); no flag, hint text or personal data is ever in an event or the buffer.
- The Lua script needs Valkey 7 or later (explicit stream ids and `XTRIM MINID` are used; the stack runs 9.0.6).

- Real stack: see the dev-log (an event row to an open stream through the web origin, the heartbeat, isolation, replay after the API was stopped, resync, the snapshot).
