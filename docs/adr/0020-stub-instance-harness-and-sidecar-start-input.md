# 0020. Stub instance, lab harness and sidecar start input

- **Status:** Accepted for the stub design and the sidecar start input (confirmed by Tanmay on 2026-10-10, recorded in the L-06 plan). **Proposed** for points 4 and 5 under Decision (found while building, not yet confirmed).
- **Date:** 2026-10-10
- **Deciders:** Tanmay (stream L). Akshay and the L-13 and L-20 stories confirm the sidecar input.
- **Requirements:** IF-6 (instance contract), IF-4 (event contract), OI-35 and handoff H-59 (sidecar start input), H-74, H-56, D-37, ADR 0005, ADR 0016, ADR 0017. Report row LB-6.

## Context
Sahil (T-04) and the lab needed a reference instance to build against before any real instance component exists, and nothing proved that the instance contract (IF-6) and the event contract (IF-4) work together. The sidecar start input was also still open (OI-35): IF-6 said the sidecar gets an event key, flag digests and `first_seq` on standard input but gave no shape.

## Options considered
1. **Real components now** (Caddy edge, real gate, real sidecar) - proves more, but L-12, L-13, L-15, L-20 and T-04 own them; far too large for L-06.
2. **A shell or BusyBox stub** - small, but cannot validate the posted schema, sign with HMAC or keep a retry buffer without more tools.
3. **One small Node image with six commands** (five instance roles, `shop`, `inject`, `sidecar`, `edge`, `gate`, plus the harness-only `ingest` wrapper), real behaviour only where a contract needs it (chosen).
4. Sidecar input as environment variables or a file - rejected: keys and flags never go in the environment (IF-6 s2), and a file on a volume would be visible to other containers.
5. **Keeping the tmpfs volumes alive** (proposal): (a) a helper "volume keeper" container started first (chosen for the harness; small, outside the instance role rules, but one more container); (b) ordinary disk-backed named volumes - rejected, IF-6 requires memory-backed storage; (c) start the shop together with the injector - rejected, the shop must start only after the injector exited 0; (d) let the injector never exit - rejected, IF-6 says it exits and is removed.
6. **Ending the start document** (proposal): (a) read to end of input - hangs with Compose-made containers (observed); (b) create containers by hand with `docker create -i` (sets `StdinOnce`) - would duplicate the hardening flags that the compose file states once and the conformance check reads; (c) the document ends at the end of input or at the first complete JSON object, anything after it is a bad document, with a 10 second read deadline (chosen).

## Decision
1. **One stub image**, `contracts/mocks/stub-instance/`, a Node 24.21.0 Alpine base pinned by multi-arch index digest, Ajv 8.20.0 and ajv-formats 3.0.1 installed at build time (the only dependencies, pinned as in `package.json`). Test only; never pushed, never a product image. Built from the repository root with a `Dockerfile.dockerignore` allowlist.
2. **Real behaviour only where the contract needs it.** Shop: `/healthz`, `/readyz` (marker and open database), `/version`, plus a clearly marked test route set under `/_stub/`. Injector: the IF-6 s5 steps and exit codes. Sidecar: the IF-4 s3 to s6 answers, `seq` from `first_seq`, HMAC signing, keep-or-drop retry rules, bounded buffer. Edge and gate: pass-through (the relay passes only `POST /internal/v1/events`).
3. **Sidecar start input (OI-35, H-59), a proposal:** one JSON document on standard input, read once, schema `contracts/instance/sidecar-start.schema.json` (`schema_version`, `instance_id`, `epoch`, `first_seq` at least 1, `event_key` 32 to 128 printable ASCII characters, `flag_digests`), at most 64 KiB, strict UTF-8. Additive (IF-6 0.1.3).
4. **Volume keeper (proposal).** A Docker `tmpfs` local volume is unmounted, and its content lost, when the last container that mounts it stops. The injector exits before the shop starts, so the harness starts a helper container (`volume-keeper`: the four volumes read-only, no network, does nothing) first and removes it with the project. It is labelled `vm.kind=harness`, so it is outside the instance role rules. L-13 needs an equivalent or another way (IF-6 OP 36).
5. **Input ends at the first complete JSON object (proposal).** A container made through Compose has no `StdinOnce` flag (observed: `docker inspect` shows `OpenStdin=true`, `StdinOnce=false`), so Docker does not close its standard input when the writer is done and a read-to-end hangs. The stub reads until the end of input or until one complete JSON object has arrived; data after the object, a value that is not an object and input that is not complete after 10 seconds are bad documents (exit 2 for the sidecar and ingest wrapper, exit 10 for the injector). The orchestrator, creating containers through the Docker API, should set `StdinOnce`.
6. **The fake ingest in the harness reads its key and instance id from standard input** (the same start document), through a small wrapper (`ingest` command), not from `--key`, so the test key is not in a command line, a compose file or `docker inspect`. The fake ingest keeps its `--key` option. This is the sixth command (five instance roles plus the harness-only ingest wrapper), a deviation from the five commands of the plan text.
7. **The harness** (`node scripts/dev.mjs harness`, `infra/compose/harness.yaml`, a separate Compose project `vulnmart-harness`) follows the IF-6 runtime profile and is checked by `scripts/check-instance-conformance.mjs` on the resolved config (static rules) and on the running stack (live probes and `docker inspect`). Fresh fake flags, seed and key are generated at each run and reach containers only on standard input.

## Consequences
- Sahil can build the real shop and injector against a running reference and run the same conformance check on his own output.
- The conformance check turns the runtime profile into code: a broken copy (bind mount, writable root, extra capability, wide port, injector with network) fails with the rule's name.
- Findings 4 and 5 are real obligations for L-13 (orchestrator) and are written into IF-6 (section 7, OP 36) and H-93.
- The stub shares code with the fake ingest (the sidecar imports its schema checks and signer), so a change there changes the stub.
- Watch: the numbers (memory, CPU, pids, sizes) are the example numbers of the template, placeholders until spikes S-4 and S-5.

## Evidence
Real runs, recorded in `docs/assets/l-06-stub-harness/` and in the dev-log entry `docs/dev-log/2026-10-10-tannmayygupta-stub-shop-and-lab-harness.md`.
- Observed on Docker 29.6.2 (Docker Desktop, Linux engine): a tmpfs-backed local volume lost its file when the writing container stopped (a file written by one container was absent for the next); `docker create -i` sets `StdinOnce=true` while the container Compose created had `StdinOnce=false`.
- Docker documentation read on 2026-10-10 through a summarising fetch (a small model answered a question about each page; the pages were not read in full by hand):
  - https://docs.docker.com/engine/storage/volumes/ : says only "consider using a tmpfs mount" for non-persistent data and links to a separate tmpfs page; it does not describe tmpfs-backed `local` volumes (`type=tmpfs`) or what happens to their data when the last container stops. For the `local` driver block-device example it says the path mounts "when the container starts" and the device is unmounted from the container afterwards. **Finding: the docs neither confirm nor contradict the lost-data behaviour; it rests on the experiment above (consistent with the mount-at-start, unmount-at-stop wording).**
  - https://docs.docker.com/reference/compose-file/services/ : `stdin_open` "configures a service's container to run with an allocated stdin" and "is the same as running a container with the `-i` flag"; there is no `stdin_once` or `StdinOnce` option. **Finding: confirms that Compose offers no stdin-once setting; it does not say what happens to a closed client input.** The `StdinOnce=false` value is from `docker inspect` only.
  - https://docs.docker.com/reference/cli/docker/container/run/ : `-i` "keeps the container's STDIN open"; the page does not mention stdin-once behaviour. The observation that `docker create -i` sets `StdinOnce=true` is from `docker inspect` only.
  - Nothing read contradicts the ADR. Because the docs do not confirm the two behaviours, points 4 and 5 stay **Proposed**; read the Docker Engine API reference (`StdinOnce` in the container config) before L-13 relies on them.
