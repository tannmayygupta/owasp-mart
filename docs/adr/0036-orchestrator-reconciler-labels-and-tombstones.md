# 0036. Orchestrator reconciler: Docker labels are the truth, tombstones in a small file

- **Status:** Proposed (D-55, decided on the developer's delegation; to be confirmed)
- **Date:** 2026-10-16
- **Deciders:** Tanmay (by delegation to Claude Code, story "Reconciler: repair differences between recorded and real state (spike S-13)", task L-14 part 2)
- **Requirements:** FR-INS-05, FR-INS-07, NFR-AVL-04; decisions D-54, D-52; spike S-13; handoffs H-61, H-65, H-67; architecture `docs/architecture/05-key-flows.md` section 9

## Context
The engine keeps its records in memory. After a crash or restart it forgot every instance, a half-built instance left containers, networks and volumes behind, and a destroyed id could be created again. IF-5 and IF-6 are closed (contracts 1.0.0), so no contract file may change, and the platform has no source for "the instances it wants on this host" yet.

## Options considered
1. **Where the records survive a restart.** (a) A database or a snapshot file of all records. A second source of truth that can disagree with Docker, and it would have to hold the flag-free record in full. (b) Rebuild from the Docker labels (nine labels on every object, IF-6 section 4): Docker is the only source, nothing to keep in step. Chosen: (b). What a label cannot tell (access state, who is playing) is closed and re-sent by the platform, which stays the authority.
2. **Destroyed ids after a restart (H-65).** (a) Forget them: a used id could be created again, which the contract forbids. (b) A tombstone file, one JSON line per destroyed id (instance id, epoch, time; nothing secret), appended with one write and an fsync, read at start (a torn last line is skipped). Chosen: (b). Retention is not set (H-65); the file grows by one short line per destroyed instance.
3. **Unknown instance with a complete set of containers.** (a) Destroy it (nobody asked for it). (b) Adopt it as `ready` and let the platform decide: destroy it if the platform's list does not name it. Chosen: (b). It follows the safety rule: nothing is destroyed because a list is empty or missing.
4. **Unknown instance that is incomplete (killed during a build).** Retry it (the flags are gone: they were only on the injector's standard input, so a retry cannot work) or remove it and record `failed`. Chosen: remove and record `failed` (INST-START-FAILED). The retry of failed instances is story 3.6 (OI-24).
5. **Desired state.** A port `DesiredStatePort.desired() -> set[str] | None` with a fake; the platform's source comes later (handoff for Akshay). `None`, or an error, is safe mode. Until the platform has a source the service runs with a port that wants everything: it adopts and cleans up, and never destroys for being unwanted.

## Decision
- `Backend.scan()` lists every container, network and volume with `vm.kind=inst` (name, labels, status). `reconcile.py` groups them by `vm.instance` and repairs at start (before the service answers) and about every `reconcile_interval_s` (default 60 s, in the settings port).
- Rules: objects of an instance whose build or destroy runs in this process (requested, provisioning, starting, resetting, or a destroy worker) are never touched. Old-epoch objects of a live record are removed. A live record with no object in Docker (checked again with a fresh `find`) is destroyed through the normal path. A record the platform no longer lists is destroyed through the normal path. An unknown instance is: removed silently when its id has a tombstone or it has no container; adopted `ready` when every component of its newest epoch is running, the injector is gone, the network and every volume exist; otherwise removed and recorded `failed`. An unknown template label is left alone (logged).
- Adoption: access `closed`, access epoch 0, deadline from `vm.expires` (the reaper uses it), idle limit from the settings, memory from the template plus the 64 MB keeper, and transition numbers of 1,000,000 plus the whole seconds since 2026-01-01T00:00:00Z at adoption (then one more per transition). They grow across restarts, so a second restart never numbers again from the same value and the platform's (instance, epoch, transition) de-duplication never drops a report.
- State rules (review round): a container that is restarting, paused or being removed, or whose health is still `starting`, makes the pass skip that instance (logged, looked at again next pass). Adoption needs every expected component running exactly once and healthy (or with no healthcheck), no injector, the network and every volume. Anything else with containers is incomplete: for an unknown instance it is removed and recorded `failed`; for a live record it is recorded `failed` (INST-START-FAILED, one report) and swept. A missing or unreadable `vm.expires` ends an adopted instance at the next reaper pass; a far-future one is cut to `now + max_minutes_ceiling`. The gate stays closed while a pass has an error for an instance, and the loop retries every 5 s while it is closed. A repeat of an already accepted create or reset is answered even in safe mode. A pass re-checks the records right before a removal and skips the instance when a create or reset has begun. An adopted instance cannot be reset (409 ORCH-INVALID-STATE). Without a usable `--state-dir` the tombstones are kept in memory (a loud log line `tombstones-unavailable` or `no-state-dir`).
- Safe mode: nothing is destroyed for being unwanted; incomplete leftovers are still removed; creates and resets answer 429 ORCH-BUSY until a pass has worked. The same busy answer holds from start until the first pass has finished.
- One pass failing for one instance is logged by class name and the other instances are still repaired. A pass that cannot list Docker changes nothing and keeps the engine busy.

## Consequences
Easier: restart and crash are safe without a database; the same destroy path, reports and sweep as every other destroy; every rule is tested on the fake backend and the kill case on real Docker.
Harder: the platform must tell the orchestrator which instances it wants (handoff) or no orphan is ever destroyed; an adopted instance cannot be reset (the secret-free create request is gone, the reset answers the template error) and its access is closed until the platform's next `access` call; adopted and failed records do not report to a platform that never asked for them, which the report pusher would retry for ever if the platform answers 404 (told in the handoff). A platform whose desired list is read before its own commit of a new instance could see a fresh instance as an orphan: instances in a build are skipped, a `ready` one not yet in the list would be destroyed (the handoff asks for the list to include every instance the platform has asked to create).
Deferred (review round): the tombstone append happens inside the engine lock (to move after the lock later); the idle limit of an adopted instance is fixed at adoption; the service's `AllWantedDesiredState` is a stand-in until H-123 is answered; a record in a state `_known` does not handle (stopping, left to the reaper) is only logged.
Watch: the tombstone file is local to the orchestrator host and is not backed up; losing it frees the ids of destroyed instances for the platform (the platform's database still refuses them).
