## 2. Trap 1: dashboards on Vercel, API on Oracle (cross-site cookies)
| Fact | Evidence | Status |
|---|---|---|
| IETF RFC 10017 (BCP 212, August 2026) "OAuth 2.0 for Browser-Based Applications": the BFF (backend for frontend) pattern is "strongly recommended for business applications, sensitive applications, and applications that handle personal data"; cookies must be Secure and HttpOnly, should be SameSite=Strict, should use a `__Host-` style prefix, path `/`, **no Domain attribute**; the app may be deployed on the **same origin** as the BFF, which avoids CORS preflights; SameSite alone is not enough when apps share a site (a subdomain takeover can enable CSRF); the BFF must implement CSRF defense, ideally a custom request header | [datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-browser-based-apps/) (page showed the published RFC) | VERIFIED |
| Vercel rewrites to external origins act as a reverse proxy; Vercel forwards `x-forwarded-for`, `x-forwarded-host` and similar headers; documented pattern to restrict the origin to Vercel traffic with a secret request header | [Vercel rewrites](https://vercel.com/docs/rewrites) (last updated 2026-08-11) | VERIFIED |
| **Proxied request timeout (external rewrites): maximum 120 seconds**; the error is `ROUTER_EXTERNAL_TARGET_ERROR` | [Vercel limits](https://vercel.com/docs/limits) (last updated 2026-09-16) | VERIFIED |
| Whether an SSE stream passes through a Vercel external rewrite **unbuffered** is not stated | — | NOT FOUND, needs spike S-2 |
| Third-party cookies: Chrome kept them (April 2025 decision); Safari blocks them by default; Firefox isolates cookies per site (Total Cookie Protection) | secondary sources only | UNVERIFIED |

**Recommendation:** keep the dashboards on Vercel (D-15) and make every browser call **same-origin** through a Vercel external rewrite (BFF pattern). Send the SSE stream through the same path and let it reconnect before the 120-second cap; the event IDs and replay buffer already make a reconnect lossless (D-17). The VM accepts API traffic only with a secret header that Vercel adds. Fallback if spike S-2 shows buffering: run the same Next.js app on the Oracle VM (one origin by construction); it is a configuration change.

## 3. Trap 2: the vulnerable shop must not share an origin with the platform
| Fact | Evidence | Status |
|---|---|---|
| Google's guidance for untrusted content: serve it from a **separate sandbox domain**; a domain on the Public Suffix List (PSL) gives browser-enforced isolation between tenants | [web.dev: securely hosting user data](https://web.dev/articles/securely-hosting-user-data) | VERIFIED (search result summary) |
| Cookie tossing: a sibling subdomain (or XSS on it) can force cookies onto a parent domain and even bypass HttpOnly; defense: `__Host-` prefix and no Domain attribute | [HackTricks](https://book.hacktricks.xyz/pentesting-web/hacking-with-cookies/cookie-tossing), HITCON 2019 slides | UNVERIFIED (secondary) |
| **PSL check run on the live list (downloaded 2026-10-08):** `vercel.app`, `github.io`, `duckdns.org`, `no-ip.org`, `ddns.net`, `pages.dev` are on the list; **`sslip.io`, `nip.io`, `traefik.me` are NOT** | [publicsuffix.org list](https://publicsuffix.org/list/public_suffix_list.dat) | VERIFIED |
| Let's Encrypt limits: **50 certificates per registered domain per 7 days, global across all accounts**; 5 per exact set of identifiers per 7 days; registered domain determined with the PSL | [Let's Encrypt rate limits](https://letsencrypt.org/docs/rate-limits/) | VERIFIED |
| Wildcard certificates need the DNS-01 challenge | Caddy and Let's Encrypt docs via search | VERIFIED (search) |
| DuckDNS supports setting a TXT record through its API (for Let's Encrypt), and says the TXT "will apply to all sub-subdomains"; whether `anything.name.duckdns.org` resolves for A records is not stated | [DuckDNS spec](https://www.duckdns.org/spec.jsp) | TXT VERIFIED; wildcard A UNVERIFIED (spike S-1) |
| A Caddy DuckDNS DNS plugin exists (`caddy-dns/duckdns`); it is not in the stock image and needs a custom build (xcaddy) | [GitHub](https://github.com/caddy-dns/duckdns) | VERIFIED |

**Consequence:** sslip.io names are not isolated from each other and share one global certificate limit, so they are a poor fit for per-instance certificates and for isolation. **Recommendation:** use **two separate registered domains**: one for the platform and one for lab instances, for example two DuckDNS names (each is its own registered domain because `duckdns.org` is on the PSL). Instances live at `<id>.<labs-name>.duckdns.org` with **one wildcard certificate** (DNS-01, Caddy with the DuckDNS plugin), so no per-instance issuance and no rate-limit problem. If a real domain arrives (GitHub Student Pack), use two registrable domains the same way (not two subdomains of one). Platform cookies use `__Host-` names with no Domain attribute. Last-resort fallback: IP certificate and one port per instance on a single lab hostname, with the platform on a different hostname.

## 4. Trap 3: instances have no route out, yet events and users must get through
Facts (VERIFIED, [Docker network create](https://docs.docker.com/reference/cli/docker/network/create/)): an internal network has no default route and drops traffic to other networks; the gateway IP and host services stay reachable. Docker's default address pools allow about 31 networks (documented defaults and community reports; **UNVERIFIED count**), so `default-address-pools` must be changed before creating two networks per instance ([Docker networking overview](https://docs.docker.com/engine/network.md)).

**Recommendation:** each instance gets **two internal networks**. `app`: shop, mock services, import service, bot and the sidecar. `ctl`: the sidecar, the platform-side **edge proxy** and the platform-side **collector**. The edge proxy and collector (two separate containers) are attached to each instance's `ctl` network with `docker network connect`, which works the same on Linux and on Docker Desktop. The sidecar pushes signed events to the collector over `ctl`; the collector validates schema, size and signature and forwards to the platform ingest API over a separate internal platform network. Nothing in `app` can reach `ctl`, the database, Valkey, the orchestrator or another instance. Rejected: one shared ingest network for all sidecars (lateral movement), a route out for the sidecar (breaks D-23), unix sockets (unreliable across Docker Desktop on Windows and macOS, UNVERIFIED). Keep the host-side drop rule (D-23). The collector must treat sidecar input as untrusted.

## 7. Recommendation (lifecycle)
Use **a Scrum-lite cadence** (one-week sprints, short planning, review and retrospective, a written Definition of Done that includes tests and docs) with a **GSD-style execution loop for every task** (plan from a story file, implement in a fresh context, verify, one atomic commit, update docs and tracker), and **BMAD's idea of story files**. Skip BMAD's analysis and planning phases (done). **Avoid shared mutable files between developers:** one tracker folder per stream, plus a generated read-only overview. **Tracker in the repo as files**, updated by Claude Code rules and hooks, because `gh` is currently logged in with the work account and the project rule is SSH only with no tokens. Prefer **our own small slash commands and hook** that follow the GSD loop over installing the third-party package, which injects prompts into Claude Code with the developer's permissions and is unreviewed; try GSD in a throwaway branch first if desired.
